# MEPLE — the Maine Platform for Legislative Engagement

A static, data-driven site for reading and publishing testimony on bills before
the Maine State Legislature, adapted from [MAPLE](https://mapletestimony.org)
(Massachusetts). Stewarded by the Center for Engaged Citizenship at the
University of Southern Maine.

Live site: https://me-ple.netlify.app

## Layout

```
site/            what gets deployed (Netlify publish dir)
  index.html     the whole app: hash-routed, no build step, reads ./data/*.json
  data/          generated by the pipeline (committed so deploys are plain static)
    meta.json, committees.json, legislators.json
    bills/index.json            one compact row per bill (search/filter/sort)
    bills/LD{n}.json            everything about one bill (loaded on demand)
    testimony/index.json        one row per testimony document (no text)
    testimony/LD{n}.json        extracted text for every document on that bill
pipeline/        Python; pulls the public record and writes site/data
  config.py      session number + every URL pattern we rely on (verified/UNVERIFIED flags)
  legiscan.py    LegiScan dataset -> LD list, sponsors, history, roll calls, hearing calendar
  crawl_bills.py / bills.py   Legislature status pages -> committee history, reports, amendments, disposition
  billtext.py    printed bill PDFs -> the official SUMMARY section
  rosters.py     House/Senate rosters and committee membership
  testimony.py   discover the testimony endpoint, index documents, download PDFs, extract text
  normalize.py   Maine vocabulary -> site statuses; position inference rules
  build.py       merge everything -> site/data
run.py           the whole thing in order (python run.py); run.sh is the same for bash
```

## Data sources and what each contributes

| Source | Used for | Access |
|---|---|---|
| legislature.maine.gov bill status pages (`display_ps.asp?LD=…&snum=132`) | committee work-session history, committee reports with signers, amendments and fiscal notes, final disposition, printed-document links | public, no key |
| legislature.maine.gov printed bills (`getPDF.asp`) | the official SUMMARY written by the Revisor's Office | public |
| legislature.maine.gov testimony feeds (`getTestyCmte.asp` → `getTestyCmteDates.asp` → `getTestyForCmteHearingDate.asp`, PDFs via `getTestimonyDoc.asp`) | every written testimony filed with a committee (name, organization or town, LD, hearing date, PDF) | public JSON, no key |
| legislature.maine.gov rosters (House `ExportActiveMembers?format=csv`, Senate `district-listing` + district profile pages) | towns, leadership, committee membership and chairs | public |
| LegiScan dataset for the 132nd (CC BY 4.0) | LD list, sponsors/cosponsors with stable ids, chamber-by-chamber history, roll calls with per-member votes, hearing calendar, subject tags | free API key: put `LEGISCAN_KEY=...` in a `.env` file at the repo root (see `.env.example`) |
| Open States / Plural | cross-check only | free API key (`OPENSTATES_KEY`), optional |

Testimony shown under "Legislature's record" was filed through the
Legislature's own submission system. Testimony submitted through MEPLE is
stored and labeled separately. Positions are shown only when the Legislature
recorded one (`position_source: filed`); if a position is inferred from the
text of the testimony it is marked `inferred` and rendered with an asterisk.

**How positions are inferred** (`python -m pipeline.testimony positions`,
also run at the end of `extract`; rules in `pipeline/normalize.py`). Bills
heard together often get the same letter filed under each of them, so a
stance only counts for a bill when the phrase names that bill: "in support of
LD 1822", "oppose LDs 1224, 1088, and 1284", "LD 1822 -- Ought to Pass",
"Position on LD 1822: Against", a sponsor "introducing LD 1822", or "in
opposition to the bills before the committee" (every bill the letter is filed
under). A stance that names no bill ("please vote ought to pass") is used only
when the document is filed under one bill and states no stance on any other.
Otherwise the position is left blank. Documents are matched as the same letter
when the witness, hearing date, committee and extracted text are identical;
each row gets `shared_with` (the other LDs) and each bill gets `heard_with`.

Measured 2026-11-07 against a manual read of every document (by Claude, while building this): LD 1822 (58
documents, heard with LDs 1088/1224/1284) 57/58 correct, up from 46/58; a
random sample of 60 documents from other bills 49/60 correct with the
bill-specific rules alone and 54/60 after adding the "these bills" and closing
-ask phrases found while reviewing that sample (that second figure is tuned on
the same sample, so treat it as optimistic). In both sets every remaining
error but one is a blank where the position is implicit ("we are concerned
about LD 1822", "Stop these stupid bills") or stated only deep in a long
letter; the other is a label from an ambiguous "vote in favor of these bills".
No support/oppose reversals remained. Every labeled row says "inferred".

**Legislators who left.** The House member list keeps former members marked
"Resigned" or "Deceased"; `rosters.py` reads the date from each profile and
`build.py` sets `current: false`, `served_until`, `left_reason` and
`replaced_by` (the current member for the same district, or null while the seat
is vacant). `meta.json` counts current members only. Tribal representatives are
not in the House CSV export and are taken from the list page.

**Organization vs. town.** The Legislature's testimony feed has no town field:
its one free-text `organization` field holds whatever the witness typed, which
for individuals is usually their town. `testimony.split_org_town()` moves a value
to `town` when it is a Maine municipality or township (the House district-towns
list, saved by the `rosters` step), a village of one ("Kittery Point", "South
China"), or an out-of-state "City, ST". Everything else stays `organization`. A
row therefore has one or the other, never both.

**Who testified** (`pipeline/profiles.py`, after `build`): organizations named on
2+ testimonies, state agencies and public bodies, and officials testifying for
them. Legislators are not given organization profiles ("Maine State
Legislature", "House District 15"); they have legislator pages. Name variants
that were merged are listed in `pipeline/raw/profiles_review.json`; add
non-obvious ones to `ORG_ALIASES`. Officials get a person profile only in
senior roles (commissioners and deputy/associate/acting commissioners; heads of
independent agencies and authorities; constitutional officers; commission chairs
and members; bureau or office directors), judged from the title written next to
their name or in their self-introduction. Staff (policy director, legislative
liaison, general counsel, analyst, deputy director) count only on the agency's
profile. An agency is inferred from a letter's text only when the organization
field is blank or itself an agency.

**Lobbying** (`python -m pipeline.lobbying index`, then `python run.py
lobbying`) reads the Ethics Commission portal's own API
(`api.mainelobbying.com/api/advanced-search/monthly-report/bills-and-issues` and
`.../compensation-for-lobbying`, 100 rows per page; about 9 minutes). The
Commission's "lobbying year" runs December to November, so lobbying years 2025
and 2026 cover the 132nd; the site shows calendar months. Checked 2026-11-07
against the Commission's per-bill search for LD 1822: the same 91 clients; the
Commission lists 3 more reports (all Google LLC) that are missing from its
monthly-report datasets.

**Campaign finance** is not loaded yet. mainecampaignfinancedisclosure.com is
behind a Cloudflare browser check (no automated download), its public datasets
cover 2026 only, and it says data for reports filed before December 2025 is
available on request from the Ethics Commission. Put the 2024-cycle exports in
`pipeline/raw/finance/candidates.csv` and `transactions.csv`, then run `python
run.py finance`.

**Testimony synthesis.** `pipeline/synthesis.py` (Batch API, needs
`ANTHROPIC_API_KEY`) is not run yet. `synthesis_manual/` holds hand-written
syntheses in the same JSON format (LD 1822, 676 and 1840, written by Claude Opus
5.5 after reading every letter on each bill). `python -m pipeline.synthesis
build` validates them (every cited id is a letter on that bill with text, every
count equals the ids cited) and copies them into `site/data/synthesis/`, so
rebuilding keeps them.

## Running the pipeline

Needs Python 3.11+, `pip install -r requirements.txt`, `playwright install chromium`,
and optionally `pdftotext` (poppler); without it, PDF text extraction falls back to
pypdf, then pdfplumber, which are slower but work everywhere. Network access to:

- `legislature.maine.gov` and `mainelegislature.org`
- `legiscan.com` / `api.legiscan.com` (if using LegiScan)
- `v3.openstates.org` (optional)

### Checking the parsers

All URL patterns in `pipeline/config.py` were verified against the live site on
2026-11-06. If the Legislature changes its pages, these debug commands show what
the parsers see:

1. `python -m pipeline.bills --ld 1822 --debug`: compare the parsed JSON with the
   status page and fix the selectors in `bills.py`.
2. `python -m pipeline.testimony discover`: logs the XHR calls the testimony
   pages make; update `TESTIMONY_ENDPOINTS` if they change.
3. `python -m pipeline.rosters --debug`: dumps the roster HTML.
4. Check the committee codes in `config.COMMITTEES` against
   `phwksched.html?CODE=…` links (Criminal Justice is `CJPS`).

Then `python run.py` (or `./run.sh` on a Mac/Linux shell). Steps run in order:
`legiscan`, `crawl`, `billtext`, `rosters`, `tindex`, `textract`, `build`, then
the phase-2 steps `pages`, `profiles`, `lobbying`, `finance`, `synthesis` (see
PHASE2.md; lobbying and finance skip until their inputs exist). If one
fails, fix it and re-run just that step and the ones after it, e.g.
`python run.py textract` and then `python run.py build`. Every step caches
downloads under `pipeline/raw/` (gitignored), so re-runs only fetch what is new.
A full first run of the 132nd (2,245 bills, about 45,000 testimony PDFs) takes
most of a day, mostly PDF text extraction; later runs take minutes.

### Moving to the 133rd Legislature (convenes December 2026)

Change `SESSION`, `LEGISLATURE_LABEL` and `YEARS` in `config.py`, update
`COMMITTEES` if the joint rules change the committee list, and re-run. Bill
status pages for the new session start appearing once LDs are printed in
January 2027.

## Deploying

**Method: Netlify continuous deploys from this repo.** Everything the site needs
is committed, including the extracted testimony text, so the `main` branch alone
is the deployable site. Netlify publishes the `site` folder with no build
command (`netlify.toml` says this). Do not also deploy from this machine with
`netlify deploy`: a manual deploy would be replaced by the next push.

This was chosen because the data fits comfortably in git. Measured after the
2026-11-07 build:

| | Size |
|---|---|
| `site/data` total | 230 MB |
| testimony text (`site/data/testimony/LD*.json`, 2,121 files) | 172 MB |
| largest file (`site/data/testimony/index.json`, 1.2 MB gzipped) | 13 MB |
| largest per-bill text file (`LD210.json`) | 5.6 MB |

The rule was: commit the text while it stays under about 250 MB total with no
file over 50 MB (GitHub's warning size). If a later session goes past that, add
`site/data/testimony/LD*.json` to `.gitignore`, run `git rm --cached` on those
files, deploy with `netlify deploy --prod --dir=site` from the machine that ran
the pipeline, and turn off builds in Netlify (Site configuration → Build & deploy
→ Stop builds) so the two methods can't overwrite each other.

Cloudflare Pages also works; note its 20,000-file limit per deployment, which is
why testimony text is bundled per bill rather than per document.

### Refreshing the data

1. `python run.py`. Cached pages are reused; new bills, hearings and testimony
   are fetched. To re-read pages that have changed (status pages update as bills
   move), delete `pipeline/raw/bills/LD*.json` first, or run
   `python -m pipeline.crawl_bills --refresh`.
2. Check the step summaries at the end of the log, then serve `site/` locally
   (`python -m http.server --directory site`) and open the home page, a bill
   with testimony (e.g. `#/bill/1822`) and `#/testimony`.
3. `du -sh site/data site/data/testimony` to confirm the size rule above still
   holds.
4. `git add site/data && git commit -m "Refresh data" && git push`. Netlify
   deploys the push.
